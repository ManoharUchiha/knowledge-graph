Repository Intelligence Platform

How code becomes a queryable graph for LLM agents.

1. Indexing flow

flowchart LR subgraph Input A[Repository directory] end A --> B[GitRepository] B --> C[repo / branch / commit / root_path] A --> D[RepositoryScanner] D --> E[FileInfo list] E --> F[ParserFactory] F --> G[PythonParser] F --> H[YamlParser] F --> I[TerraformParser] G --> J[Symbols + Relationships] H --> J I --> J J --> K[Resolver] K --> L[Crossplane XRD/Composition/Function links] K --> M[Python imports / calls / inheritance] K --> N[Module-qualified references] L --> O[RepositoryModel] M --> O N --> O O --> P[GraphBuilder] P --> Q[Neo4j graph]
  • GitRepository extracts repo metadata (name, branch, commit, root path).
  • RepositoryScanner walks files and maps extensions to languages.
  • Parsers produce symbols and relationships (classes, functions, resources, XRDs, Compositions).
  • Resolvers link loose references into concrete graph edges.
  • GraphBuilder batches writes into Neo4j using MERGE for idempotency.

2. Query & consumption flow

flowchart LR subgraph User A[Devin / CLI / MCP client] end A -->|natural language or CLI| B[MCP Server] A -->|command| C[CLI] B --> D[GraphQueries] C --> D D --> E[Neo4j] E --> F[structured JSON] F --> B B --> A
  • CLI is used for indexing and ad-hoc queries.
  • MCP server exposes the same queries as tools for LLM agents like Devin.
  • GraphQueries resolves absolute paths to repo-relative paths and runs Cypher queries.
  • Neo4j returns structured evidence (file paths, line numbers, relationships).

3. Optional supporting systems

flowchart TB A[Indexer / Query layer] --> B[OpenTelemetry tracing] A --> C[Investigation memory SQLite] A --> D[Vector store] D --> E[InMemoryVectorStore] D --> F[Qdrant stub]
  • OpenTelemetry traces indexing and query operations.
  • Investigation memory (SQLite/SQLAlchemy) persists sessions and findings.
  • Vector store currently uses an in-memory keyword fallback; Qdrant is stubbed for future semantic search.
